Optimizing Django QuerySets & Eliminating the Dreaded N+1 Problem

Ganga Sagar Joshi
Sep 2026
4 min read

Django's Object-Relational Mapper (ORM) provides powerful developer ergonomics, but its lazy evaluation model can quietly trigger the infamous N+1 query antipattern. A view rendering 50 items can inadvertently execute 51 or even 151 individual SQL statements, choking the database connection pool.

1. What Causes the N+1 Antipattern?

When you loop over a QuerySet and access a foreign key or related relation that was not eagerly loaded, Django fires a separate SQL query for each single record in the iteration:

# Antipattern: Fires 1 query for clinics + 50 queries for doctor details!
clinics = Clinic.objects.all()
for c in clinics:
    print(c.head_doctor.name)

2. The Antidotes: select_related vs. prefetch_related

Understanding which technique to use based on the relational cardinalities is crucial for performance:

  • select_related (Single-valued relationships): Uses an SQL INNER JOIN or LEFT OUTER JOIN to fetch the parent and related records in a single query. Ideal for ForeignKey and OneToOneField.
  • prefetch_related (Multi-valued relationships): Executes a second targeted query using WHERE id IN (...) and joins the records in Python memory. Ideal for ManyToManyField and reverse foreign key relations.

3. Advanced Prefetching with Custom Filtered QuerySets

Use the Prefetch object when you need to order, filter, or slice the prefetched related records:

from django.db.models import Prefetch

# Fetch doctors and only their active appointments scheduled for today
today_appointments = Appointment.objects.filter(status='scheduled', date=today)
doctors = Doctor.objects.prefetch_related(
    Prefetch('appointments', queryset=today_appointments, to_attr='todays_schedule')
)

Result

By replacing naive iteration with targeted eager loading, API response times commonly plummet from 800ms down to under 45ms, while reducing database CPU consumption by over 90%.
